## 6. 用户数据处理的技术描述（边界）

| 环节 | 处理 | 删除边界 |
|---|---|---|
| 本地存储 | 应用私有数据库（RDB，`com.bp.recorder`），无账号、无服务端 | 「清空数据」只删本应用数据库 |
| 系统通知 | 通知内容含药品名/剂量与时间（本地通知与代理提醒） | 关闭通知或卸载后不再存在 |
| 主动导出/分享 | 三份 CSV（交换格式）与完整备份 JSON；分享走系统分享面板 | 导出文件在**用户选择的位置**，应用不删除 |
| 相册副本 | 保存长图写入系统相册 | 属于系统相册，**清空业务数据不会删除**；临时图在 cacheDir，按 24h / 50MiB 清理 |
| 健康图像缓存 | `cacheDir` 内本应用前缀文件 | 有配额清理，失败不静默 |

## 6.5 平台事实（真机实测，写代码时必须知道）

| 事实 | 后果与对策 |
|---|---|
| **事务内用 `store.query` 读不到本事务尚未提交的写入** | 在 `runInTransaction` 里"回库自查刚写的数据"会拿到旧状态（实测：刚插入的计划查不到、刚启用的药品仍 inactive）。对策：把刚写入的对象**直接传给**下游（见 `SavedMedicationPlan`），不要回库查。 |
| **事务内做不传 `TxSession` 的写入 = 自我死锁** | 该写入会去排自己已持有的串行队列 → 永久挂住（端侧表现为 5 秒超时）。现在 `BpDatabase.txDepth` 会**显式拒绝**并提示把 `tx` 传下去。 |
