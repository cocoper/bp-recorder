## C. 用户裁决项（已确认）

### C1. 报告「打印 / PDF」采用纯 ArkUI 同源渲染
- **背景**：策划 §4.1 写「报告页 Web 容器渲染 → 系统打印界面」，§4.2/§5.10 写报告页为 ArkUI 页面并整页 `componentSnapshot` 出长图，两者不能同时按字面成立。
- **裁决**：方案 A —— 报告只做一套 ArkUI 渲染，`componentSnapshot` 出 PNG，长图 / 分享 / 打印三路共用同一张图。
- **实现位置**：`pages/ReportPage.ets`（容器 `id = bp_report_capture`）、`service/ShareService.ets`
- **影响**：不引入 Web 组件，少一套排版维护；FR-10.3 三输出、§5.10 长图、§4.1「打印框架 + 另存为 PDF」全部满足，仅舍弃「Web 容器」这一句实现备注。

### C2. 趋势图心率曲线使用独立右副轴
- **背景**：§5.3 原文给的是「心率单独副轴 **或** 归一化标注」。
- **裁决**：方案 A —— 右副轴，心率有独立刻度。
- **实现位置**：`components/BpLineChart.ets` 的 `yHr()` 与右轴刻度绘制；关掉 `showHeartRate` 时右侧留白自动收窄。

### C3. 配色支持浅色 + 深色双套
- **背景**：§4.2 要求颜色资源化，全文未提及深色模式。
- **裁决**：方案 B —— 双套颜色资源（`resources/base/element/color.json` 与 `resources/dark/element/color.json`，各 53 个键，键集合经脚本校验一一对应）。
- **衍生决策（重要）**：图表卡片与报告正文使用**印刷配色**（`print_*` 系列，两套主题下取值完全相同：白底、深字、固定曲线色）。理由：
  1. FR-11.4 要求分享图「背景纯白」，FR-10.3 要求打印产物可读，若跟随主题则深色模式下分享图会变成黑底，与要求冲突；
  2. 让「应用内预览」与「分享/打印产物」像素级一致，用户不会遇到「看到的是这样、发出去是那样」；
  3. 无需为出图做二次渲染或临时切换主题。
- **代价**：深色模式下图表卡片与报告纸张仍是白底，观感上是「浮在深色页面上的纸」。这是为满足分享/打印要求主动接受的取舍。

## A. 对策划文档的事实性纠正

### A1. 代理提醒权限名不是 `ohos.permission.REMINDER_AGENT`
- **文档原文**：§4.1 与 NFR-5 均写作 `ohos.permission.REMINDER_AGENT`。
- **事实**：API 12 不存在该权限名，正确名称为 **`ohos.permission.PUBLISH_AGENT_REMINDER`**（官方文档与开发者社区一致）。若按原文声明，工程无法编译。
- **处理**：`module.json5` 按正确名称声明。
- **第二个事实（回合 4 已更正，原文说重了）**：官方权限列表明确 `ohos.permission.PUBLISH_AGENT_REMINDER` 的**权限级别是 normal、授权方式是 system_grant**，属面向所有应用开放的权限 ——
  即**声明后安装时自动授予，不会阻塞编译或安装，也不需要为它改用手动签名**。
  真正的不确定性在**运行时**：部分设备 / ROM 对「代理提醒」加了**管控机制**，`publishReminder()` 可能返回 `1700001`（能力未开通）。
  因此策划文档 M4 阻塞项的正确定性是「**可用性因设备而异、需真机实测**」，而不是「必然不可用」；探测失败时回退 NotificationKit 即为实际主路径。
  > 原文曾写「受管控能力 → 必须手动签名 → 自动调试签名下必然失败」。该表述缺少官方依据（官方权限列表写的是 normal / system_grant），属过度断言，已在回合 4 更正。
- **实现**：`ReminderService` 两条路径都实现 + 运行时真实探测（发布一条 10 秒倒计时提醒后立即取消）+ 结论缓存 + 自动回退；设置页展示当前生效方式。申请开放能力的步骤见 `docs/运行与部署说明.md`。

### A2. 打印需要 `ohos.permission.PRINT`
- **文档原文**：§4.1 的权限清单只有代理提醒一项（NFR-5 也只要求「不申请任何网络权限」）。
- **事实**：`print.print()` 缺少 `ohos.permission.PRINT` 时返回错误码 201。
- **处理**：在 `module.json5` 中补充声明。该权限属**本机能力权限、与网络无关**，因此不违反 NFR-5 的零网络权限原则。若机型不支持打印，长图与分享两条输出不受影响（策划 §10 已把长图列为保底输出）。

### A3. `med_log` 需要唯一约束才能实现「预生成幂等」
- **文档原文**：§3.1 描述「预生成滚动推进、幂等，已存在则跳过」，但表结构中没有任何能支撑该性质的约束。
- **处理**：增加 `CREATE UNIQUE INDEX uidx_medlog_med_time ON med_log (medication_id, scheduled_time)`。
- **实现**：`BpDatabase.insertMissingLogs()` 先查出窗口内已存在的 `(药品, 计划时间)` 组合，只插入差集，再用 `INSERT OR IGNORE` 兜底双保险。返回值是**实际新增条数**（而非尝试插入条数）。
- **验证**：Hypium `BpDatabaseTest.medication_plan_log_crud` 断言第二次预生成新增数为 0。

### A4. 时段文案与 CSV 文案必须资源化，因此服务层需要接收「词表」
- **冲突**：CL-7 要求「字符串/颜色全部资源化，代码无中文硬编码」，而 §4.2 与 §10 又要求「文案锁死在 `Constants.ets`」。CSV 表头与状态文字（附录 A）必须是固定中文，且导入时要按原文比对。
- **处理**：两者同时满足 —— `Constants.ets` 保存**资源引用**（`$r('app.string.xxx')`），实际字面量在 `resources` 中；由 `common/Vocab.ets` 的 `VocabFactory` 在页面侧解析成字符串词表，作为参数传给服务层。
- **收益**：`ExportService` / `ImportService.parseXxx` / `ReportService` 保持**纯函数**（不触碰 `resourceManager`），因此「导出 → 原样回导」的幂等性可以在本机离线用例中真实验证（见 `docs/自检报告.md` 的 CL-10 证据）。

### A5. 附录 A 的打卡状态枚举不足以支撑往返幂等
- **问题**：附录 A 只列了 `已服用 / 已服用(补记) / 跳过 / 漏服`。若严格照此导出，未到期的 `pending` 记录无处安放：要么丢行（违反数据完整），要么导出后无法回导（违反 CL-10 幂等）。
- **处理**：增加第五个状态文字 **`待服`**（`csv_status_pending`），导出与导入双向支持。
- **验证**：离线用例断言「6 条含 pending 的打卡记录导出后原样回导 → 0 错误、重复数 = 总条数」。

# 回合 2 变更记录 —— 响应《审查意见》（v1.2 项目策划方案）

> 完整分析见 `docs/审查意见回应.md`。本节只登记**新产生的实现决策**及其可核验内容。

## F. 本轮新增决策

### F1. `bp_record` 与 `med_plan` 增加数据库级唯一约束（P1-4）
- **决定**：`SCHEMA_VERSION` 1 → 2，迁移中建两条唯一索引：
  `uidx_bp_triple (measure_time, systolic, diastolic)` 与
  `uidx_plan_active_med (medication_id) WHERE is_active = 1`。
- **理由**：FR-6.6 的判重三元组与 FR-8.2 的"每个药品一条生效计划"此前只活在应用层，重试/并发下无结构保障。
- **关键实现细节（不得简化）**：建唯一索引前**必须先清理历史脏数据**（删除同三元组重复记录、把同一药品的多余生效计划置停用），且整个迁移包在一个事务里。原因：`CREATE UNIQUE INDEX` 在脏数据上会失败，而该步骤位于**启动初始化路径**且无容错，失败后果是**应用起不来**。
- **连带行为变更**：手工录入的三元组与已有记录完全相同时被拒绝。为避免用户看到无信息量的数据库错误，录入页增加 `existsBpTriple()` 前置检查并给出明确提示（`err_duplicate_record`）。
- **验证**：Hypium `unique_triple_index_enforced`、`exists_bp_triple_precheck`。

### F2. 计划变更时清理"失效的未来待服记录"（P1-3）
- **决定**：新增 `BpDatabase.deleteFuturePendingLogs(medicationId, now)`，删除边界**严格限定**为 `status='pending'` 且 `scheduled_time > now`。
- **理由**：计划修改/停用后，按旧计划预生成的未来 pending 已不成立，不清会造成"计划已改、旧提醒与旧卡片还在"，并污染依从率分母。
- **边界为何这样定**：
  - 只删 `pending` —— 已服/跳过/漏服属历史记录，永不删除（FR-8.3）；
  - 只删**未来** —— 过去的 pending 是当时真实存在的服药义务，保留后会自然派生为漏服并计入依从率分母，抹掉它反而失真。
- **调用点**：计划保存、停用计划、归档药品（三处）。
- **验证**：Hypium `delete_future_pending_logs_only` 断言三类记录的各自去留。

### F3. 第三条回退路径：进入前台时补发漏服提醒（P0-1）
- **决定**：代理提醒不可用时，`EntryAbility.onEnterForeground()` 统计当日漏服数，按**自然日去重**发一条补发通知（`ReminderService.notifyCatchUpOncePerDay`）。

- **两处细节**：
  - 导入时"每日次数"列会与"时间点"实际数量**交叉校验**，不一致按错误行报告，**不静默纠正**；

## L. v1.14 事实性纠正：`1700001` 的含义，以及「提醒注册」与「提醒响」是两件事

### L1. `1700001` 不是「设备 / ROM 管控」，就是「通知未使能」

- **本文件原文（A1 第二条 / D4 / B24 一带）**：把 `publishReminder()` 的 `1700001` 解释为「部分设备 / ROM 对代理提醒加了管控机制（能力未开通）」，并据此判断「代理提醒在自用场景基本不可用、本地通知才是主路径」。
- **事实（v1.14 依据 SDK 与官方文档更正）**：
  1. SDK `@ohos.reminderAgentManager.d.ts` 中 `publishReminder` 的 JSDoc 原文：*"This API can be called only after the notificationManager.requestEnableNotification permission is obtained."*
  2. 官方错误码表：**`1700001 Notification is not enabled` = 通知使能未开启**，可能原因只有两条 —— 未申请通知使能权限、或应用的通知开关被关闭；处理办法就是调 `requestEnableNotification` 并让用户在通知设置里打开开关。
  3. `ohos.permission.PUBLISH_AGENT_REMINDER` 依旧是 `system_grant` / `normal` / `provisionEnable: true`（A1 已记录）—— 声明即可，无需 AGC 开放能力、无需手动签名。
- **处理**：删掉 `module.json5` 里「需 AGC 申请开放能力 + 改手动签名」的注释，改为指向通知授权前置条件；策划方案 §4.1 表格两行与 FR-9.1 同步更正；本文件 A1 第二条、D4 的「基本不可用」判断**作废，以本节为准**。
- **教训**：把「自己没做的那一步」解释成「平台不给」，会直接导致功能静默失效 —— 本轮就是如此（见 L2）。

### L2. 「保存了计划」≠「系统里登记了提醒」：幂等缓存不能用来证明登记成功

- **现象**：用户「设置了用药提醒，但是没有生效」。真因是三条叠加：`publishReminder` 需要通知授权（L1）→ 全应用**只有设置页那一行**会请求授权（首启与保存计划都不请求）→ `ReminderService.rebuildAll()` 在 `mode !== AGENT` 时直接 `return`（不发布、不记签名、界面无感知）。从未进过设置页的用户必然一条提醒都没有。
- **决策**：
  1. **前置条件必须由流程主动取得**：保存服药计划时调 `ReminderService.ensureNotificationEnabled()`（已授权直接返回、不弹窗）；未授权时明确提示，不谎报成功。**并且必须照顾「改之前就已经设置过」的老用户**：只挂在保存动作上，他不重新保存就永远走不到修复路径，因此在启动时补一次 —— `EntryAbility.onEnterForeground()` 第 2b 步：当天有生效时点、方式非 AGENT、通知未授权、且本次安装从未问过（`Prefs.NOTIFY_ASKED`）→ 请求授权 → 成功则 `rebuildAll(..., force = true)`。**每次安装至多弹一次**系统框，用户拒绝后不再骚扰（改为警示卡 + 设置页如实告知）——这条折中是「自己的前置条件」与「不打扰用户」之间的取舍。
  2. **失败必须可见**：用药页在「有计划时点但通知未开 / 已登记提醒为 0」时显示警示卡；设置页显示**已登记提醒条数**（`getAllValidReminders().length`）与「最近探测」详情。
  3. **幂等缓存的判据要落在系统状态上**：`rebuildAll()` 的签名描述的是**计划内容**，登记与否是**系统状态**；因此签名相同但有效提醒为 0 时必须重建（签名自愈），且只在真正发布成功（`published > 0`）或当天确实无可发布时点时才记签名。
- **推翻的旧假设**：B24 的「签名幂等」本身正确，但它隐含的前提是「上一次一定发布成功」——该前提在授权缺失时不成立，故补自愈条件。

### L3. 仍未修的已知边界（如实登记）

- `ReminderRequestAlarm` 只支持按周重复、**没有结束日期参数**：每日闹钟用 `daysOfWeek: [1..7]` 无限重复，因此计划 `end_date` 过后、**若应用不再被打开，提醒仍会继续响**（下次进入前台 `cancelAllReminders()` + 重新发布才会消失）。B25 的判断在这一层仍然成立，v1.14 只是把它写得更明确。
- 本轮改动**未在真机验证**：授权框 → 到点响铃全链路（含息屏/锁屏）、拒绝授权时的警示与文案、已登记提醒条数、签名自愈、**启动时补请求一次（且拒绝后不再重复弹）**。证据与未验证清单见 `docs/自检报告.md` §27。

- **口径细节（容易被写错，故显式登记）**：`end_date < 今天 00:00` 才算到期 —— **今天到期不算**（当天仍要按计划提醒），与 `isPlanActiveOn` 的 `end ≤ day` 互补；`end_date` 为 NULL / 空 / 非法一律按长期处理（**宁可不停用，也不误停用**）；已是停用状态的不重复计数。
- **`expiredEndDate()` 故意不看 `isActive`**：自动停用后计划就是 `is_active=0`，而用药页恰恰需要在这个状态下告诉用户「它是到期停用的」，否则用户只会看到「未设置服药计划」。
- **残余边界（仍未解决，属平台能力）**：用户从此不再打开 App 时，系统侧无法自清 —— 已登记在策划第 10 章风险表与 §L3。
