## 2. 逐项核对结论

### P0-1 提醒回退方案本身可能不成立 —— **成立；已补上第三条路径**

**我的独立发现**（实现时）：`ohos.permission.REMINDER_AGENT` 这个权限名**不存在**，真实名称是 `ohos.permission.PUBLISH_AGENT_REMINDER`。

> **（回合 4 更正）** 我最初接着写道「该能力属受管控、需在 AGC 申请并改用手动签名，因此调试签名下不可用是可预判的」。
> 核对官方权限列表后更正：该权限为 **normal 级 / system_grant**，声明后**安装即授予、不阻塞编译与安装、也不要求手动签名**；
> 不确定性在**运行时** —— 部分设备 / ROM 有管控，`publishReminder` 可能返回 `1700001`。
> 所以正确定性是「**可用性因设备而异、需实测**」，而非「必然不可用」。
> 相应地，把这一项列为"P0 阻塞"的前提也弱化了：**它不阻塞开工，只需要把回退路径实现好** —— 而这一点原实现已经做到。

**我对审查意见前提做的进一步事实核查**（它说 NotificationKit 不提供精确的未来定时唤醒）：核实 `NotificationRequest.deliveryTime` 时发现**资料冲突**：

| 来源 | 说法 |
|---|---|
| 基于 API 12+ 的实践文章 | `deliveryTime` 是**系统落库时自动生成的时间戳**，写未来时间不会延迟发送；且本地通知由应用进程发布，**进程不存活就发不出来** |
| 基于 API 23 的文章 | `deliveryTime` 可由开发者设置，交给系统 Alarm 调度，**应用被杀也能弹出** |

两者不可能同时为真，最可能是 `deliveryTime` 在较晚的 API 版本才变为可写。**我们目标 API 12，因此保守取值**：不依赖该字段。审查意见的前提成立，并新增真机实验项 **V1b**（在目标 SDK/ROM 上验证 deliveryTime 是否可写且能延时送达）。

**已采取的动作**（不只是"扩验证范围"）：

1. 实现了**第三条回退路径** —— `ReminderService.notifyCatchUpOncePerDay()` + 接入 `EntryAbility.onEnterForeground()`：代理提醒不可用时，进入前台若当日存在漏服，按自然日去重发一条补发通知。
   选择这条路径的理由：它是**唯一 100% 可用、不依赖任何系统能力授予**的触达方式。审查意见举的"引导用户用系统日历/时钟"实际上是**把职责推给用户**，不能算 App 的能力。
2. 采纳"不允许静默降级"的精神：回退模式下设置页显示明确的能力边界说明（`reminder_fallback_hint`），并明示"提醒只能在应用运行时送达"，而不是让用户以为提醒仍然准时。

**我不选甲、也不选乙，建议方案丙**：

| 项 | 方案丙的规则 |
|---|---|
| 分级（色标 + 分级名） | **永远只用诊室表**。理由：中国指南的分级表本身就是诊室血压的分类表，它是唯一有出处、能给出"1/2/3 级"名称的表 |

### P1-2 M3 依赖 M4 才存在的功能 —— **成立**

M3 要求完成"用药打卡 CSV 导出"，而 `med_log` 的写入方在 M4。我实现时是并行写服务层，所以没有实际受阻，但计划顺序确实自相矛盾。同意把用药打卡导出移入 M5。

### P1-3 计划变更后已预生成的 pending 无处置规则 —— **成立，且命中了已交付代码的真实缺陷**

**核实过程（可复现）**：全工程检索无任何清理未来 pending 的逻辑；`MedPlanEditPage.save()` 只做「停用旧计划 → 写新计划 → 差集补生成」，**从不清掉按旧计划生成的未来待服记录**。

**症状**：把计划从 `07:30 / 18:00` 改成 `12:00` 后，今天与未来 7 天内仍残留 `07:30 / 18:00` 的 pending —— 首页「今日服药」卡片会显示**已不存在的服药安排**，且这些残留会进入依从率分母，把依从率算低。

**已修复**：新增 `BpDatabase.deleteFuturePendingLogs(medicationId, now)`，删除边界严格限定为 **`status='pending'` 且 `scheduled_time > now`**：

- 只删 pending：已服 / 跳过 / 漏服属历史记录，永不删除（FR-8.3）；
- 只删未来：**过去**的 pending 是当时真实存在的服药义务，保留后会自然派生为漏服并计入依从率分母，抹掉它反而失真。

调用点三处：计划保存、停用计划、归档药品。新增 Hypium 用例 `delete_future_pending_logs_only` 断言三类记录的去留。

### P1-4 关键唯一性约束缺失 —— **成立；已修复，并顺手把"版本化迁移"从空壳变成真迁移**

**核实**：`bp_record` 的判重只活在 `ImportService` 的内存集合里；`med_plan` 的"每个药品一条生效计划"只活在 `upsertPlan` 的应用逻辑里。数据库层零保障。

**已修复**：`SCHEMA_VERSION` 1 → 2，迁移中做三件事：

1. 清理同三元组（`measure_time + systolic + diastolic`）的重复血压记录，保留最早一条；
2. 同一药品若有多条生效计划，只保留最新一条，其余置停用；
3. 建立两条唯一索引：`uidx_bp_triple (measure_time, systolic, diastolic)` 与 `uidx_plan_active_med (medication_id) WHERE is_active = 1`（部分唯一索引，SQLite 3.32+ 支持）。

**必须补上的一句话（审查意见的疏漏）**：只写"加约束"是不够的，**必须先清理历史脏数据再建索引**。原因：`CREATE UNIQUE INDEX` 在已有脏数据的库上会失败，而这一步位于**启动初始化路径**且没有容错 —— 后果不是"约束没建成"，而是**应用直接起不来**。因此正确顺序是「清理 → 建索引」，并整体包在一个事务里（已如此实现）。

**连带行为变更**：手工录入的三元组与已有记录完全相同时，现在会被拒绝。我在录入页加了**前置检查** `existsBpTriple()` 给出明确提示（"已存在相同测量时间与数值的记录"），而不是让数据库抛约束错误让用户看到无信息量的"保存失败"。这条规则文档没写，**请确认接受**。

### P1-5 "漏服自动标记"的实现路径未定义 —— **成立（对文档而言），但实现本来就走的是推荐做法**

我实现的就是审查意见推荐的方案：`MedService.resolveStatus()` 是**读时派生的纯函数**（超时 2h → missed），`BpDatabase.markMissed()` 只在前台做一次**机会性落库**。没有引入 `workScheduler`、没有后台定时任务、没有额外耗电。

→ **不需要改代码**，只需在 v1.3 的 §3.4 写明"missed 为读时派生状态，落库与否均可，统计口径以派生结果为准"。

### P1-6 阈值口径与分级标准切换不一致 —— **部分成立：事实描述成立，但建议的修法会引入医学错误**

**事实层面审查意见是对的**：FR-5.3 写死 135/85、FR-10.2 写死 140/90，都不随 FR-7.1 切换。

**但我不建议按它说的"两处都改为跟随当前分级标准"。理由是：135/85 是"测量场景"属性，不是"用户偏好"属性。**

- 中国指南中 140/90 是**诊室血压**的诊断阈值；135/85 是**家庭自测血压（多次均值）**的诊断阈值；
- 本 App 的数据**全部是家庭自测**；
- 因此 7 天均值用 135/85 判定在医学上是正确的，与用户选了哪个"分级标准"无关；
- 若改成"选中国指南时用 140/90"，等于**用诊室阈值判家庭数据**，会系统性低估、漏报 —— 这是把一个正确设计改错。

**但审查意见的底层诉求我完全接受**：文档必须把这件事写明确，包括它指出的 **FR-5.3 中"≥A/B"的歧义**（我的实现是按"收缩压 ≥A **和/或** 舒张压 ≥B"做的，但文档确实没写清）。

**关键结论：P1-6 与 P0-2 是同一个根因** —— 文档把"家庭自测标准"当成了第二套完整分级表。**P0-2 一旦按方案丙解决，P1-6 自动消失**：不存在第二套分级表了，135/85 只作为"家庭自测场景阈值"存在，也就不需要跟谁"一致"。

### P1-7 录入时间缺少未来时间校验 —— **成立（对文档）；代码已实现，但决策记录漏登记**

实现时已加入：`BpValidator.validateForm()` 拒绝晚于当前时间 60s 以外的测量时间（资源 `err_time_future`），日期选择器上限也设为今天。离线断言覆盖"未来 2 分钟被拒绝 / 5 年前被接受"。

### P1-8 打印/PDF 路径双重实现 —— **成立，且已由你的裁决关闭**

### P1-9 导出覆盖面不完整、换机闭环断裂 —— **成立；已补做第三个 CSV**

**核实**：原实现导出只有血压 CSV 与打卡 CSV，药品档案与服药计划确实无导出；且导入打卡只会建**停用**档案（这正是 FR-6.7 的规定）。所以换机后计划全丢，依从率与今日卡片都是空的 ——迁移场景只闭环了一半。

**已补做**：新增第三个文件「用药计划 CSV」（药品 / 剂量 / 每日次数 / 时间点 / 开始日期 / 结束日期 / 备注），导出与导入双向实现：

- `ExportService.buildPlanCsv()`（每药品一行，时间点用分隔符连接）；
- `ImportService.parsePlanTable()` + `commitPlan()`，判重键为「药品名 + **规范化后**的时间点集合」——因此库内时间点顺序与文件不同也能正确判重；
- 导入后**立即滚动预生成打卡记录并重建提醒**，否则新计划不产生应服记录；
- "每日次数"列会与"时间点"实际数量**交叉校验**，不一致按错误行报告，不静默纠正。

**验证**：新增 19 条离线断言，含往返幂等（原样回导 → 0 新增、重复数 = 总条数）与 8 行脏数据的逐行隔离（7 错 1 有效）。

**关于文档 §8.3 的过期段落**：确认是 v1.2 遗留文字（"如需迁移可走导出 CSV → 二期做导入"），应删除。

## 5. 我认为这份审查意见可以补强的 4 点

1. **P1-4 漏了"建约束前必须清理脏数据"这一步**，而漏了它的后果不是"约束没建成"，而是**应用起不来**（建索引位于启动初始化路径且无容错）。正确做法是"先清理 → 后建索引 → 整体一个事务"。
2. **P0-2 漏了它对 CL-6 的连带影响**：采纳甲/丙后，"切换分级标准后色标刷新"这条验收项必须同步改写，否则 v1.3 会带着一条不可能通过的验收项开工。
3. **P1-6 的修法方向会引入医学错误**：把家庭自测均值预警改为跟随用户的"分级标准"，等于允许用**诊室阈值**判**家庭数据**，会系统性漏报。正确做法是把"场景阈值"与"用户偏好"分离。
4. **P0-1 的第三条预案过于笼统**：它举的"引导用户用系统日历/时钟"是把职责推给用户，不能算 App 的能力。真正可落地且必须做的是**"打开 App 时补发"**——唯一 100% 可用、不依赖任何系统能力授予的触达方式。本轮已按此实现。
5. **放行条件的表述需要调整**：本项目实现已完成，v1.3 不应"重新走开工流程"，而应以**变更单**形式打补丁（哪些改文档、哪些改代码、哪些仅登记接受）。
