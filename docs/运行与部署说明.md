## 4. 编译与真机安装

### 4.1 首次打开

1. DevEco Studio → **File → Open**，选择**工程根 `BpRecorder`**（不是它的上级目录）。
2. 等待 hvigor 同步完成（无三方依赖，同步很快）。
3. 若提示 SDK 缺失：**File → Project Structure → SDK** 指定 API 26（HarmonyOS 26.0.0）。

#### ⚠️ 硬性约束（一）：路径字符（踩过一次，务必先看）

DevEco 打开工程时会先校验**工程路径的字符**，允许的只有：
**字母、数字、句点 `.`、反斜杠 `\`、下划线 `_`、连字符 `-`**，且不能以句点结尾。
**空格和中文都不允许** —— 违规时弹出的「路径无效，请选择只包含字母、数字、句点(.)、反斜杠(\\)、下划线(_)和连字符(-) 的路径，且不能以句点结尾」，工程**根本打不开**（这是路径校验，不是编译错误）。

本项目早期位于 `.../workbuddy/BP recorder/BpRecorder`，其中父目录名 `BP recorder` 含**空格**，正是违规字符。

**最终布局**（工程是**单份真实目录**，任何位置都不再留符号链接）：

| 用途 | 路径 |
|---|---|
| **工程根 —— DevEco 打开这个** | `/Volumes/ZT700-Data/Projects/workbuddy/BP-recorder/BpRecorder` |
| 项目根（文档 + 工具 + 记忆） | `/Volumes/ZT700-Data/Projects/workbuddy/BP-recorder/` |
| 同层别名（**不要用来打开工程**） | `/Volumes/.../workbuddy/BP recorder` —— 本工作区别名，是**符号链接**，仅为兼容旧引用而保留 |

#### ⚠️ 硬性约束（二）：工程目录**不得经过任何符号链接**（更隐蔽，代价更大）

这一条比字符要求更难发现，症状是「**能打开、但同步失败**」：

- 欢迎页能进、「最近项目」里有记录、左侧工程树也完整显示出来；
- 但通知里报 **「检测到不合法的依赖。请移除外部依赖中不是 HAR 或 HSP 类型的模块。」**，项目同步中断，
  Run / 构建因此不可用。

根因（已在 DevEco 26.0 的 `plugins/openharmony/lib/ohos-project-model-*.jar` 中定位到）：

- 该提示来自 `CheckProjectImlFile.checkOuterModule`，判断依据是**模块路径是否落在工程目录之内**；
- 走符号链接时，工程路径是 `/Volumes/.../BpRecorder`，而 `entry` 模块的真实路径被解析成
  `/Users/.../BpRecorder/entry`，两者前缀不匹配 → `entry` 被判为「外部模块」；
- `entry` 是 HAP、不是 HAR/HSP → 命中消息 `invalid.dependency.module.type.error`，
  抛 `SyncInterruptException` 中断同步（日志见 `~/Library/Logs/Huawei/DevEcoStudio26.0/idea.log`）；
- 附带症状：hvigor 写出的 `.hvigor/dependencyMap/dependencyMap.json5` 中 `basePath` 是**真实路径**，
  而 IDE 读取的 `.hvigor/outputs/sync/fileCache.json` 是**符号链接路径** —— 同一个工程出现两个根路径。

**结论：工程必须是单份真实目录，且其路径上每一段都不得是符号链接。**
本项目曾采用「项目根下的 `BpRecorder` → 内盘工程」的符号链接方案，即因此同步失败；
现已改回单份真实目录，并已清空在错误路径下生成的 `.idea`、`.hvigor`、`oh_modules`、`oh-package-lock.json5`。

#### ⚠️ 同步失败的另一种：`build-profile.json5` 的 SDK 版本字段被写成空值

它和路径无关，而且**这个值是 IDE 自己写坏的，不是人工改的**：工程同步时 DevEco 会对工程做一次
「API 配置升级」，可能往 `products[].targetSdkVersion` 写入**空字符串** `""`。空串匹配不上 IDE 内部的
版本号正则，于是同步直接中断，通知报：

> 同步失败：`compileSdkVersion、compatibleSdkVersion或targetSdkVersio（若显式配置）的值不正确，请按照指南中的说明修改该值。`

（对应消息键 `project.check.dotApi.format.error`；抛错点 `HosIntegrationChecker.checkApiVersionFormat`。
 注意该文案里的 `targetSdkVersio` 少个 `n`，是官方原文自带的笔误，可用于对号。）

**正确写法**（与 DevEco 26.0 自带工程模板
`Contents/plugins/codegenie-plugin/previewProjectTemplate/build-profile.json5` 一致）：

```json5
"products": [
  {
    "name": "default",
    "signingConfig": "default",
    "compatibleSdkVersion": "26.0.0",
    "targetSdkVersion": "26.0.0",        // 显式给出，且与 compatibleSdkVersion 同值
    "runtimeOS": "HarmonyOS"
    // ...
  }
]
```

> **版本号格式（API 26 起变更，易踩）**：不再写 `26.0.0(26)` 这种带括号格式。
> 写成 `26.0.0(26)` 时 hvigor 报 `00308018 api version parameter is illegal!
> Expected format: <major>[.<minor>][.<patch>]`。
> 判定规则取自本机 SDK 源码（`@ohos/sdkmanager-common` 的
> `DOT_API_VERSION_PATTERN` 与 `FIRST_DOT_API_VERSION = 26`）：主版本 ≥ 26 用点分制，以下用旧格式。
> `tools/check-project-config.mjs` 已内置两套正则并会与本机 SDK 比对。

三点要点：

- `targetSdkVersion` 显式给出、**非空**、格式为 `x.y.z(n)`；
- **不要**在 `app` 字段下配置 `compileSdkVersion` / `compatibleSdkVersion` / `targetSdkVersion` ——
  v26 的 schema 里 `app` 只允许 `signingConfigs` / `products` / `buildModeSet` / `multiProjects` 四个键；
- 版本号写**字符串**（当 `runtimeOS` 为 `HarmonyOS` 时）；只有 `runtimeOS` 为 `OpenHarmony` 才是整数。

`tools/check-project-config.mjs` 会用**与 IDE 完全相同的正则**校验这三个字段，并检查
`targetSdkVersion` 与 `compatibleSdkVersion` 是否同值，可在打开工程前先跑一遍拦住它。

### 4.2 配置自动化签名（真机安装的**必做**步骤）

**交付版本的** `build-profile.json5` 里 `signingConfigs` 是**空数组** —— 这是**正常状态，不是缺陷**：
签名材料包含本机绝对路径与证书口令，不可能随源码交付。未配置签名前构建会停在"未签名"。

> **本机当前状态（2026-10-06 22:46 实测）**：签名**已配置**。
> `signingConfigs[0].material` 指向 `~/.ohos/config/default_BpRecorder_*.p12 / .cer / .p7b`；
> 档案类型 `debug`、bundle `com.bp.recorder`、有效期 **2026-10-06 → 2027-10-06**。
> 执行 `node tools/install-to-device.mjs --list` 可直接读出这些信息与「登记了哪些设备」。

**自动签名必须同时满足三个前提**，缺一条就会失败（三种失败的报错各不相同，便于对号入座）：

| 前提 | 不满足时的表现 |
|---|---|
| ① 已用华为开发者账号登录 IDE | 签名面板空白，或提示登录 |
| ② 账号**已完成实名认证** | 通知栏报 **「该功能仅限实名认证的开发者使用。」** |
| ③ **已连接真机且被 hdc 真正识别** | 提示 **「缺少设备导致无法新建 profile 文件，请先通过 IP 或 USB 连接设备」** |

> 实名认证在华为开发者联盟网站完成，**个人开发者即可、免费**；它只用于签发证书，与是否上架无关。

操作步骤：

1. **File → Project Structure → Signing Configs**；
2. 勾选 **Automatically generate signature**；
3. 登录华为开发者账号（若提示未实名，先去完成实名认证再回来）；
4. 确认设备已连接 —— 用 `hdc list targets` 验证（见 4.3），IDE 需要把该设备的 UDID 写进 Profile；
5. 首次会弹出同意协议，确认即可；
6. 点 **Apply / OK** —— IDE 会把 `signingConfigs` 与 `products[].signingConfig` 自动写回 `build-profile.json5`。

> **只用模拟器 / 预览器的话可以完全跳过本节** —— 官方说明：使用模拟器和预览器调试**无需签名**。
> 因此在实名认证办好之前，也可以先用模拟器把 App 跑起来看效果。

> 若后续改了 `bundleName`（当前 `com.bp.recorder`）或换了手机，**必须重新勾选一次自动签名**重新生成 Profile，
> 否则会出现"安装成功但打不开、日志报 signature failed"。

#### ⚠️ 关键：档案里**登记了哪些设备，才能装到哪些设备**（最容易踩、报错最难看懂的一个坑）

调试签名档案（Profile）内有一个 `debug-info.device-ids` **白名单**，只有列在其中的设备能安装这个 HAP。
在 DevEco 勾选自动签名时，IDE 把**那一刻 `hdc` 能看到的设备**写进白名单 —— 由此产生三种情况：

| 签名时的连接情况 | 结果 |
|---|---|
| 只连了模拟器 | 出来的包装**模拟器**没问题，装**实体手机**必然失败 |
| 只连了手机 | 反之亦然（模拟器会失败） |
| 设备与模拟器**都连着** | 两台都写进白名单，都能装（白名单支持多台） |

**查白名单（不需要打开 DevEco）**：

```bash
node tools/install-to-device.mjs --list
```

它把「hdc 当前看到的设备」与「档案里已登记的 UDID」**逐台比对**，给出 ✓/✗ 与下一步提示；
不带 `--list` 时会对已登记的设备直接安装。

> **本机 2026-10-06 22:46 实测**：档案登记 1 台，型号 `emulator` —— 即签名时只连了模拟器。
> 因此**当时那份签名包装不到实体手机上**，要装手机必须先按 §4.3 连好手机，再重新自动签名一次。

> 想手工核对，可用 DevEco 自带工具解出档案（本机已验证可用）：

### 4.5 能不能把 HAP 直接发给别人安装？（常见问题）

**不能 —— 鸿蒙与 Android 的 APK 分发模型不同。** 这一点值得单独说明，因为它直接决定「能不能像 APK 那样发个文件过去就装」：

| | Android APK | HarmonyOS HAP |
|---|---|---|
| 未签名能否安装 | 能（勾选「未知来源」） | **不能**，系统直接拒绝安装 |
| 调试签名能否装到任意设备 | 能 | **不能**，Profile 内绑定了 UDID 白名单 |
| 分发方式 | 任意渠道传文件 | **必须经 AGC 签名**（上架 / 开放式测试） |

具体到本项目：

1. **调试签名的 HAP 只能装到「签名时已注册 UDID 的设备」**。在 DevEco 中勾选自动签名时，IDE 会把**当时连着的那台手机**的 UDID 写进 Profile，因此「自己编译 → 装自己的手机」完全没问题；但同一个 HAP 发给另一台手机就会报
   `error: signature verification failed due to not trusted app source`（错误码 `9568322`）。

   > **另一个易混的错误码 `9568332`（`install sign info inconsistent`）**：这不是"设备没登记"，
   > 而是**设备上已装的旧版本用了另一套签名材料**。重新生成过签名材料（例如又点了一次「自动签名」、
   > 或换了账号/证书）之后覆盖安装旧包，就会报这个。两种处理：
   > - **可以丢弃旧数据**：先 `hdc -t <设备> uninstall com.bp.recorder`，再安装；
   > - **要保留数据**：改用 DevEco 的 Run 按钮（IDE 会处理覆盖安装）。
   > 本机 2026-10-06 22:51 在模拟器上实测命中过该错误码。
   > 判定"到底是没登记还是签名材料变了"，跑 `node tools/install-to-device.mjs --list` 即可区分。
2. 要让别的设备也能装，必须走**发布证书 + 发布 Profile**（需实名开发者认证），或通过应用市场的开放式测试渠道分发 —— 那属于「分发」，不是「安装」。
3. **APP 包更不行**：官方明确「APP 包只能用于发布，即便使用调试证书和调试 Profile 签名，也无法安装」。

所以本项目的正确路径就是 §4.1–§4.4：**在你自己的电脑上装 DevEco → 用你自己的华为账号自动签名 → Run 到你自己的手机**。
这条路上**不需要你手工查 UDID 或申请证书** —— 勾选自动签名后 IDE 会自动完成注册与签发。

### 5.10 导入预检与「让别人帮你导数据」

**拿到任何一份 CSV（别的 App 导的、别人帮你做的、手写的），先在电脑上预检再传手机**：

```bash
node tools/check-import-file.mjs <csv 路径>
```

它直接调用工程里**真实的解析实现**（不是另写一份规则），输出：

1. 严格格式三种类型各自的有效行数（血压记录 / 用药打卡 / 用药计划）；
2. 「其他来源」模式的**列自动识别结果**（哪一列被认成什么）与有效行数；

## 6. 代理提醒的可用性（**不影响安装**，仅在需要系统级提醒时才要申请）
**先澄清一个容易误解的点**：`ohos.permission.PUBLISH_AGENT_REMINDER` 的**权限级别是 normal、授权方式是 system_grant**，
属于面向所有应用开放的开放权限 —— **声明后安装时即自动授予，不会导致编译失败或安装失败**。
（`ohos.permission.PRINT` 同样为 normal / system_grant。）

真正的不确定性在**运行时**：部分设备 / ROM 对「代理提醒」加了**管控机制**，
`reminderAgentManager.publishReminder()` 可能返回 `1700001`（能力未开通）。因此本应用：

- **首次使用时做一次真实探测**（发布一条 10 秒倒计时提醒后立即取消），失败即自动回退到本地通知，结论缓存进 Preferences；
- 设置页「服药提醒」一行显示当前生效方式，回退时同时展示能力边界说明（`reminder_fallback_hint`）。

**如果探测失败、且你希望启用系统级代理提醒**（App 未启动 / 锁屏也能触发），才需要走下面的申请流程：

1. 登录 **AppGallery Connect** → 选择项目与对应的 HarmonyOS 应用；
2. **项目设置 → 开放能力管理** → 找到「代理提醒」→ 点「申请」；
3. 填写申请原因（生活服务 / 健康类的**服药提醒**场景），上传：
   - 展示提醒设置界面的截图（本应用的「用药管理 → 编辑服药计划」页面）；
   - 从「应用上架 → 应用信息」页截取的应用分类截图；
4. 提交后约 8 个工作日反馈；通过后勾选能力开关并保存；
5. **按 AGC 的反馈指引更新签名**：若申请通过后要求 Profile 携带该能力，DevEco 会提示重新生成 Profile，按界面提示操作即可（`Signing Configs` 界面会给出对应入口）；
6. 重新编译安装后，打开 App → **设置 → 服药提醒**，点一次触发重新检测，应显示为「代理提醒」。

未完成上述申请时，设置页显示「本地通知」，并给出说明文案（`reminder_fallback_hint`）——这是**预期行为**，不是缺陷。

## 10. 常见问题

**Q：编译报找不到 `$r('app.string.xxx')`？**
运行 `node tools/check-resources.mjs`，它会列出所有未定义或被引用但不存在的键。

**Q：设置页显示「未授权」？**
点「通知权限」一行申请通知授权；若已被系统永久拒绝，需到系统设置中手动为应用开启通知。

**Q：提醒不准时？**
系统省电策略可能延迟通知。建议把应用加入「受保护应用」/关闭电池优化（设置 → 应用 → 血压助手 → 耗电管理）。

**Q：换手机后数据没了？**
单机版设计如此。请先在旧机「导出数据」**分三次**导出「血压 / 用药打卡 / 用药计划」CSV，在新机用「导入数据」逐份恢复。**只导出血压与打卡是不够的** —— 药品档案与服药计划无法由此迁移，新机上的依从率与今日服药卡片都会是空的（这正是 FR-6.9 / FR-6.10 存在的原因）。

**Q：编译报某个服务层函数「参数个数不对」？**
运行 `node tools/check-api-usage.mjs`，它会定位到具体文件与行号 —— 通常是服务层改了签名而 UI 层漏改，这类问题在本机类型检查里是盲区。

**Q：升级安装后应用起不来（旧版本已有数据）？**
v1→v2 迁移会在启动时新增两条唯一索引，且已按「先清理脏数据 → 再建索引 → 单事务」实现。若确实启动异常，先用 `node --no-warnings tools/sqlcheck.mjs` 确认迁移逻辑本身无误，再排查设备上 `relationalStore` 封装的行为是否与预期一致。

**Q：想上架华为应用市场，需要做什么？**
完整工作清单见 **`docs/上架华为应用市场-工作清单.md`**。三条最关键的结论：

1. **无需 APP 备案** —— 官方对「单机应用」（未通过公共互联网提供信息服务）豁免备案，本项目零网络权限，完全符合；这一个条件就省掉了约 5–25 个工作日的流程。
2. **瓶颈是软件著作权**（20–40 个工作日）与「应用创建受邀名单」申请（2026 年新规，3–5 个工作日）—— 都要**最先启动**。
3. **代码侧只需改造一项**：首启**隐私政策弹窗需提供「同意 / 不同意」二选一**（当前只有「知道了」单按钮，不符合上架要求）。其余（API Level、包格式、包内无调试信息、体积、versionCode）均已满足。

> 注意区分：**自用走调试签名，几小时即可完成**（不需要上面任何资质）；**上架走发布签名 + 全部资质，约 6–8 周**。上架的唯一意义是能分发给别人且不受设备 UDID 限制。
